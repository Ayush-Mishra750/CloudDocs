## 3. ACTIVE MILESTONE PROMPT

# MILESTONE 1: Project Initialization & Core Infrastructure

## Objective
Set up the foundational monorepo structure for CloudDocs AI with a working, Dockerized backend (Node.js + Express) and frontend (React + Vite + Tailwind), connected to MongoDB and Redis. No business logic (auth, files, etc.) is implemented yet. The goal is a clean, production-standard skeleton that boots via Docker Compose, exposes a health-check API, and has logging, error handling, and environment configuration wired up correctly. This milestone establishes the architecture every future milestone will build on.

## Features to Build
- Monorepo structure with `/backend` and `/frontend` as independent services
- Express server with modular structure (routes, controllers, middlewares, config, utils)
- MongoDB connection via Mongoose with retry/error handling
- Redis connection with retry/error handling
- Centralized environment variable configuration (`config/env.js`) with validation on boot
- Centralized error-handling middleware (JSON error responses, no stack leaks in production)
- Centralized logging (Winston or Pino) with request logging (Morgan) writing to console + rotating log file
- `/api/v1/health` endpoint returning service, DB, and Redis status
- React + Vite + Tailwind frontend skeleton with React Router set up (Home page + NotFound page)
- Axios instance pre-configured with base URL and `withCredentials: true`
- React Query provider wired at app root
- A simple "System Status" page in frontend that calls `/api/v1/health` and displays backend/DB/Redis status (proves full-stack connectivity)
- Docker Compose orchestrating: backend, frontend, MongoDB, Redis — all networked together
- `.env.example` files for both backend and frontend
- ESLint + Prettier config for both backend and frontend
- Root-level `README.md` explaining how to run the project locally via Docker

## API Routes
| Method | Route | Description | Auth Required |
|---|---|---|---|
| GET | `/api/v1/health` | Returns `{ status, uptime, timestamp, services: { mongo: 'connected'|'disconnected', redis: 'connected'|'disconnected' } }` | No |

No other routes in this milestone.

## Database Schema Changes
None. No Mongoose models are created in this milestone. Only the MongoDB **connection** is established and verified via the health endpoint.

## Redis Usage
- Redis client connection established at server boot (`config/redis.js`) using `ioredis` or `redis` npm package.
- No keys are written in this milestone — Redis is only used to verify connectivity (`PING` command) for the health check.
- Redis connection config must support both local Docker (`redis://redis:6379`) and future cloud Redis (e.g., AWS ElastiCache) via `REDIS_URL` env var.

## AWS Usage
None in this milestone. AWS S3/CloudFront wiring begins in Milestone 5. However, reserve `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` as placeholder env vars in `.env.example` for forward compatibility (unused for now).

## Docker Changes
- `docker-compose.yml` at root defines 4 services:
  - `backend` (build from `./backend`, port `5000:5000`, depends_on `mongo`, `redis`)
  - `frontend` (build from `./frontend`, port `5173:5173`)
  - `mongo` (image `mongo:7`, volume `mongo_data:/data/db`, port `27017:27017`)
  - `redis` (image `redis:7-alpine`, volume `redis_data:/data`, port `6379:6379`)
- Named volumes: `mongo_data`, `redis_data`
- Custom bridge network: `clouddocs_network`
- `backend/Dockerfile`: multi-stage (deps → dev) using `node:20-alpine`, hot-reload via `nodemon` in dev stage
- `frontend/Dockerfile`: `node:20-alpine`, runs Vite dev server exposed on `0.0.0.0`
- `.dockerignore` for both services (excludes `node_modules`, `logs`, `.env`)

## Validation
- On backend boot, `config/env.js` validates all required env vars are present using a simple schema check (e.g., `envalid` or manual validation). If any required var is missing, the process logs a clear error and exits with code `1`.
- No request-body validation needed yet (no POST/PUT routes in this milestone) — but install and configure `express-validator` or `zod` as a dependency now so future milestones can use it immediately without re-setup.

## Security
- `helmet` middleware enabled globally on the Express app.
- `cors` middleware configured to only allow `CLIENT_URL` origin with `credentials: true`.
- `express.json()` body size limit set to `10kb` (prevents payload abuse) — will be revisited per-route in later milestones (e.g., file uploads).
- No secrets committed to git — `.env` is gitignored; only `.env.example` is committed.
- Docker containers run backend as non-root user (`node` user in Dockerfile).

## Error Handling
- Global `errorHandler.middleware.js`: catches all thrown/passed errors, returns consistent JSON shape:
  ```json
  { "success": false, "message": "string", "stack": "only in development" }
  ```
- `notFound.middleware.js`: handles unmatched routes with `404` and consistent JSON shape.
- MongoDB and Redis connection failures are caught, logged with full context, and do NOT crash the process — health endpoint reflects `disconnected` status instead, with retry/backoff logic (max 5 retries, exponential backoff) on initial connection attempts.

## Logging
- `utils/logger.js` using Winston (or Pino) configured with:
  - Console transport (colorized, dev-friendly format in `development`)
  - File transport writing to `backend/logs/app.log` (JSON format, for production)
- `morgan` middleware for HTTP request logging, piped into the Winston logger stream.
- Log levels: `error`, `warn`, `info`, `debug` — controlled via `LOG_LEVEL` env var.
